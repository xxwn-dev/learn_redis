# 🎟️ 선착순 티켓 구매 시스템 동시성 제어 및 성능 최적화

이 프로젝트는 대규모 트래픽이 발생하는 선착순 구매 상황에서 **데이터 정합성**을 보장하고, **시스템 성능을 최적화**하기 위한 기술적 고민과 검증 과정을 담고 있습니다.

---

## 1. 🔍 문제 정의
* **동시성 이슈**: 수천 명의 사용자가 동시에 재고를 감소시킬 때, 경쟁 상태(Race Condition)로 인해 실제 재고보다 더 많은 주문이 생성되는 현상.
* **성능 병목**: DB 수준의 락(Lock)을 사용할 경우, 트랜잭션 대기 시간 증가로 인해 전체적인 처리량(Throughput)이 저하되는 문제.

---

## 🛠️ 2. 해결 방안

### V1. DB 비관적 락 (Pessimistic Lock)
* **메커니즘**: JPA `@Lock(LockModeType.PESSIMISTIC_WRITE)`를 사용하여 데이터베이스 로우(Row) 수준에서 락을 획득.
* **장점**: 데이터베이스 수준에서 강력한 정합성 보장.
* **단점**: 동시 접속자가 많을수록 DB 커넥션 점유 시간이 길어져 병목 현상 발생.

### V2. Redis Atomic Operation (현재 채택)
* **메커니즘**: Redis의 단일 스레드 특성 기반 `DECR` 연산과 `Set` 자료구조(중복 체크)를 활용.
* **장점**: 인메모리 기반 처리를 통해 DB 부하를 획기적으로 낮추고 응답 속도를 극대화.
* **단점**: 별도의 Redis 인프라 관리 필요.

---

## 🚀 3. 성능 테스트 결과 비교 (k6)
`50 Virtual Users(VU)`가 약 9초간 반복적으로 구매를 시도한 실측 데이터입니다.

| 지표 | v1. DB 비관적 락 | v2. Redis (Atomic) | 차이 (성능 향상) |
| :--- | :---: | :---: | :---: |
| **초당 처리량 (Throughput)** | 168.79 reqs/s | **777.44 reqs/s** | **약 4.6배 향상** |
| **평균 응답 시간 (avg)** | 229.02 ms | **43.53 ms** | **약 5.3배 단축** |
| **95% 응답 시간 (p95)** | 421.9 ms | **84.44 ms** | **약 5배 단축** |
| **재고 정합성 (50개)** | 성공 (100% 일치) | 성공 (100% 일치) | - |



### 주요 분석 내용
- **사용자 경험 개선**: 유저 95%의 응답 시간(p95)을 **421ms에서 84ms**로 줄여 대기 시간을 약 80% 단축했습니다.
- **성능 수치**: Redis 도입을 통해 단일 서버 환경에서 처리할 수 있는 초당 요청 수를 **460% 이상** 끌어올렸습니다.
- **정합성 유지**: 두 방식 모두 50개의 한정된 재고를 한 치의 오차 없이 관리함을 확인했습니다.
